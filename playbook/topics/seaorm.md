# SeaORM

How a Rust crate stores data through SeaORM: dependencies, migrations,
generated entities, repositories, schema, queries and transactions. SQLite
is the backend the rules are written for; a rule that differs on Postgres,
the library's other backend
([Library architecture](../../lib/docs/architecture/library.md#41-database-backends-and-dependencies)),
says so. Imported
by the `AGENTS.md` of every Rust project that uses SeaORM.

## Dependencies

- Workspace dependencies set `default-features = false` and `runtime-tokio`
  for both crates, plus `macros` for `sea-orm`. They select no driver.
- A crate that opens SQLite connections enables `sqlx-sqlite`. A Postgres
  consumer enables `sqlx-postgres`. The library's `sqlite` and `postgres`
  features activate the respective driver on both dependencies. MCP
  forwards those features to core.
- The tables hold only INTEGER and TEXT
  ([Data model](../../lib/docs/architecture/data-model.md#3-conventions)), so no
  `with-*` feature is needed until a column needs one.
- `sea-orm-cli` runs at the version of the workspace's `sea-orm`.

## Layout

- `src/migration/mod.rs` holds the `Migrator`, which lists every migration in
  order. Each migration is one file named `mYYYYMMDD_NNNNNN_<verb>_<table>.rs`,
  such as `m20261116_000001_create_tables.rs`.
- `src/entity/` holds the generated entities, one file per table.
- `src/repository/<table>.rs` holds one table's repository, such as
  `src/repository/task.rs`.

## Migrations

- The data model docs are the schema's home: the
  [library's](../../lib/docs/architecture/data-model.md) for its migrations
  and [Lorebay's](../../docs/architecture/data-model.md) for `lorebayd`'s.
  The schema each group of migrations builds must match its doc's SQLite
  DDL, and a schema change updates that doc in the same pull request.
- Migrations use SeaORM's schema builder: `DeriveIden` enums for table and
  column names, the `schema` helpers and `SchemaManager`. Partial indexes
  use the index builder's `and_where`, and CHECK constraints the table
  builder's `check`.
- Integer columns must use the big integer type (`big_integer`,
  `big_integer_null` or `ColumnDef::big_integer`), so they are 64-bit on
  Postgres and remain INTEGER on SQLite.
- The application must generate every primary key before the insert.
  Migrations must declare TEXT NOT NULL primary keys with no auto-increment
  or database default, as
  [Data model](../../lib/docs/architecture/data-model.md#3-conventions)
  requires.
- Until the first deployment whose data must be kept, a migration merged to
  `main` may be rewritten instead of followed by a new one; a database made
  by an earlier build is then rebuilt, not upgraded. From that deployment
  on, a merged migration is never edited, renamed or reordered, and a schema
  change is a new migration.
- `down` reverses `up` and runs only against disposable databases.
- `run` applies pending migrations before it serves any request. A failed
  migration stops startup. A deployment runs one `lorebayd`
  ([Storage](../../docs/architecture/storage.md#3-layers)), so no lock
  guards the migration and no two releases share a schema.

## Entities

- `src/entity/` is generated by `sea-orm-cli generate entity` from a
  disposable projection of a SQLite file with every migration applied, and
  committed; it is never edited by hand. The generator reads a copy without
  the explicitly listed partial unique indexes it misreads as unconditional
  uniqueness; that copy is only for generation, never serving or schema
  validation.
- Generated entities are exempt from the
  [data struct rule](../languages/rust.md#errors-and-data-structures), because
  `sea-orm-cli` owns their definitions.
- A change to `src/migration/` regenerates `src/entity/` in the same commit,
  formatted with `cargo fmt`.
- The crate README's Usage section names one command that applies the
  migrations to a disposable file and generates the entities.
- Lint exceptions the generated code needs go on the `mod entity;`
  declaration as `#[expect(clippy::<lint>, reason = "...")]`, with
  sea-orm-cli named in the reason. Generated files are never patched to
  satisfy a lint.
- Entities carry no behavior, so the generated `ActiveModelBehavior` impls
  stay empty. Domain functions set IDs, keys, timestamps and derived values.
- Statuses and kinds must remain `String` in generated entities, as
  sea-orm-cli emits them. Their enum types belong in the domain layer, added
  with their first consumer. The domain layer must convert between these
  enums and entity strings at its boundary; CHECK constraints guard the
  stored values.

## Repositories

- A **repository** owns one table. It is a struct borrowing a connection,
  generic over `ConnectionTrait`, so the same methods run on the pool and
  inside a transaction.
- Repository methods take and return entity `Model`s, `ActiveModel`s and
  plain filter values, except that a read-only listing across several
  tables may return a projection struct defined beside the repository.
  They hold no business rule and never commit or roll back.
- Domain functions build `ActiveModel`s, setting keys and timestamps.
  Transports never build `ActiveModel`s.
- `run` opens one `DatabaseConnection` per process and holds it in its
  state. On SQLite, its connect options turn on foreign keys for every
  connection and set a busy timeout, so a writer waits for the current one
  instead of failing.

## Queries

Queries use the first of these that can express them:

1. SeaORM's entity API: `find` and `filter`, `insert` and `insert_many`,
   `update_many`, `delete_many`, and `on_conflict` for upserts.
2. sea-query's builders, for subqueries, CTEs, `RETURNING`, aggregates and
   `LIKE` with an `ESCAPE` character.
3. Raw SQL, only for a construct neither can express.

- Columns are named through entity `Column`s or `DeriveIden`, and values are
  bound through the builders. No value is ever formatted into a SQL string.
- Whenever a workspace crate depends on SeaORM, `clippy.toml` lists SeaORM's
  raw-SQL entry points under `disallowed-methods`: `Statement::from_string`,
  `Statement::from_sql_and_values`, `ConnectionTrait::execute_unprepared` and
  sea-query's `Expr::cust` family.
- A raw-SQL exception uses
  `#[expect(clippy::disallowed_methods, reason = "...")]` on the narrowest
  item, with a reason naming the missing builder capability.
- Queries never run once per row when a bulk form exists: read with
  `is_in`, write with `insert_many`, upsert with `on_conflict`, update and
  delete by predicate, and aggregate in SQL. Inputs are deduplicated before
  they reach a query. A per-row query that cannot be avoided carries a
  comment saying why.

## Transactions

- A transaction covers only database work. File storage calls and outbound
  HTTP requests run after the commit
  ([Storage](../../lib/docs/architecture/storage.md#4-database)).
- On SQLite, a transaction that writes must begin with
  `begin_with_options` and `SqliteTransactionMode::Immediate`, taking the
  write lock before its first read. A deferred transaction that reads and
  then writes fails with `SQLITE_BUSY` when another connection writes in
  between, and the busy timeout cannot recover it. SQLite has no
  `FOR UPDATE`; the immediate write lock takes its place.
- On Postgres, a transaction that reads a row and then writes it must lock
  the row in that read with `FOR UPDATE`. Code that runs on both backends
  does both: it begins as SQLite requires and locks as Postgres requires.
- A read that needs one consistent view across several queries runs in a
  deferred transaction; a single query needs none.

## Tests

- Integration scenarios run each test against a fresh SQLite file in its own
  data directory ([testing.md](testing.md#black-box)). The start helper
  applies migrations through `run`, as production does.
